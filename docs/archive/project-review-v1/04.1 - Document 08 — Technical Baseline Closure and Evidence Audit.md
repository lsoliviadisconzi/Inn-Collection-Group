3. Evidence and reporting standards

Every significant conclusion must be classified using the following evidence categories:

Classification	Meaning
Code-verified	Confirmed by inspecting implementation
Database-verified	Confirmed by inspecting actual database structures or records
Runtime-tested	Executed and observed successfully
File-verified	Confirmed by inspecting actual files and their contents
Inferred	Reasonable interpretation, not directly established
Proposed	Suggested future architecture or behaviour
Unknown	Insufficient evidence

Where appropriate, include:

* File paths.
* Function names.
* API routes.
* Database table names.
* Relevant implementation details.
* Test commands.
* Test results.
* Known limitations.

Do not invent test results.

Do not convert assumptions into facts.

Do not claim an integration exists simply because a component has been designed to accommodate one.

6. Important context: the next phase

This task is the final technical-baseline review before we move into a broader architectural-design exercise.

The next phase will not necessarily involve making every component fully functional.

The objective will be to establish the complete blueprint of the intended system.

That work will require us to understand and organise:

1. What already exists and should be retained.
2. What exists but needs to be connected.
3. What exists only as a prototype or mockup.
4. What capabilities are missing.
5. Which components should share data or services.
6. Which components should remain independent.
7. How the different user interfaces and environments should be organised.
8. How users move between these environments.
9. How data, operational workflows, and responsibilities connect.
10. How the overall experience should be presented visually.

We may ultimately arrive at a structure involving multiple layers, workspaces, environments, or interfaces. Do not assume that the correct answer is necessarily three layers. That architecture must be derived from the evidence and intended operational experience.

The visual experience is particularly important. The eventual system must communicate a coherent product identity and provide an excellent, understandable experience when demonstrated to stakeholders.

However, do not start designing that architecture or redesigning the interfaces in this task.

For now, preserve the evidence and close the technical baseline.
