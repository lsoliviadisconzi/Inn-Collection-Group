The six documents provide a much stronger technical picture than the earlier interface reviews. The important discovery is that this is not currently one integrated hospitality management application. It is a collection of working data-processing tools, static data outputs, a limited review database, and several front-end prototypes that describe a broader operational system.

However, I would not treat this documentation set as consolidated or technically settled yet. There are several contradictions between the documents, some claims that appear stronger than their evidence, and a few architectural recommendations that are premature.

Below is my review, maintaining the distinction between what the documents establish and what still needs verification.

1. The most important architectural finding

The actual system appears to have three distinct layers:

Layer	What it contains	Current role
Source data	Kafoodie JSON, Markdown menus, scraped website text, media CSVs, configuration files	Raw and semi-structured information
Processing and reconciliation	Python build scripts, matching logic, review tools	Cleans, compares, classifies and reconciles information
Generated outputs and interfaces	venue.json, menu-explorer-data.js, HTML interfaces	Presents or exposes processed information

SQLite sits alongside these layers, but its role is much narrower than the term application database might suggest.

According to Documents 01 and 02, the SQLite database contains just one table: issue_reviews. It stores review decisions associated with particular menu-file versions. It does not contain the actual hospitality domain model.

That distinction matters:

The system has a structured data-processing architecture, but it does not yet have a centralised operational data-management architecture.

It can reconcile menu information with recipe information and expose the results through interfaces. It does not yet provide a persistent, shared system for managing products, recipes, suppliers, pricing, EPOS configuration or launch activities.

That is a significant finding for the F&B Coordinator role.

2. Critical inconsistencies between the documents

These should be resolved before the documents are used as a technical baseline.

A. Netlify is still being treated as part of the application architecture

This is the clearest contradiction.

Your clarification was explicit: Netlify is an independent development convenience used to make interfaces accessible to agents. It can be removed without affecting the actual application.

Yet Document 05 — Component Relationships — still describes:

* netlify/functions/api.py as a production serverless service.
* AWS Lambda as part of the system’s application architecture.
* A second API server sharing the SQLite database with the local server.
* Netlify-specific behaviour as an operational dependency.

Document 01 has corrected this distinction, but Document 05 has not.

Required correction: Netlify and its serverless function should be moved into a separate development and inspection infrastructure section. They should not appear as a production service, shared runtime or required component of the actual application.

The real architecture should be documented independently of the mechanism used to expose development pages.

B. The Markdown source directories are described inconsistently

There are two conflicting accounts.

Document 05 says:

* The API servers read and modify pages/menus_md/.
* build_venue_export.py reads inncollectiongroup.com_root/menus_md/.
* The two directories can drift.

Document 01 says:

* The local server reads inncollectiongroup.com_root/menus_md/.
* The local server modifies that directory.

Document 04 also describes the review tool modifying the master directory.

These cannot all describe the same local execution path.

This is not a minor documentation issue. It affects whether a menu correction actually reaches the next build.

Required correction: Trace the actual path constants and file operations in menu_review_server.py, then establish:

1. Which directory /api/menus reads.
2. Which directory /api/menu reads.
3. Which directory /api/issues/fix-duplicates modifies.
4. Which directory build_venue_export.py reads.
5. Whether any synchronisation process exists.

Do not prescribe deleting either directory until this is established.

C. The SQLite sharing claim needs correction

Document 05 describes SQLite as shared between the two API servers.

But Document 01 says the Netlify function copies the database into ephemeral /tmp storage.

Those are different persistence models.

A local SQLite database and a temporary copy used by a serverless function are not one shared database. At most, they are separate instances initialised from the same file or seed data.

Given that Netlify is not part of the actual application architecture, the simplest correction is to document the local SQLite instance as the actual application’s review-state database and describe the Netlify copy separately, if it remains relevant to development history.

D. The number of build pipelines is inconsistent

Document 05’s overview refers to three build pipelines.

Its inventory identifies only two:

* build_menu_explorer.py
* build_venue_export.py

Documents 01, 03 and 05 otherwise consistently describe two.

Either identify the third pipeline or correct the count.

E. venue.json is not yet the canonical source of truth

This is the most important conceptual correction.

Document 05 describes venue.json as the proposed universal data source. Document 02 goes further and calls it the true canonical data model.

But the same documents establish that:

* It is generated by a build script.
* It is not consumed by any current interface.
* It is not directly maintained by operational users.
* It is derived from other sources.
* Its contents depend on matching and reconciliation logic.

A generated output is not automatically a source of truth.

I would use:

Canonical generated venue data model

rather than:

Canonical source of truth.

The distinction is important because the actual authority for each data field may differ.

For example:

Information	Current source
Recipe identifiers and recipe information	Kafoodie crawl
Printed menu descriptions	Extracted Markdown
Printed menu prices	Extracted Markdown
Venue identity and overrides	Repository configuration and crawl data
Review decisions	SQLite
Reconciled menu-to-recipe relationship	Generated venue.json

The matching between printed dishes and Kafoodie recipes is a derived relationship, not necessarily an authoritative relationship.

A future shared data layer may be appropriate, but its ownership, update rules and authority need to be established first.

3. The data model needs a more careful interpretation

Document 02 is particularly valuable because it separates concepts that are often conflated in hospitality software.

However, I would revise three classifications.

Product versus Recipe

The documents describe Kafoodie records as products and recipes interchangeably.

That may reflect the upstream platform’s terminology, but it does not establish that the concepts are equivalent.

A recipe can be used to produce a product. A product can appear on multiple menus. A menu item can have a different name, description or price at different venues.

The system should preserve those distinctions rather than inherit potentially ambiguous terminology from the source platform.

Menu Item versus Venue Offering

The proposed distinction is sound:

* A Menu Item represents what appears on a menu.
* A Venue Offering represents the availability of that item at a particular venue, potentially with local pricing and other variations.

But the generated structure needs to be examined to establish whether the relationship is actually modelled as a separate entity or simply represented by nested JSON objects.

The current documentation risks presenting a conceptual relational model as if it were a fully implemented relational database.

Ingredient and Supplier

The documentation correctly identifies the absence of structured ingredient and supplier management.

This is especially relevant to the F&B Coordinator position.

A dish containing a textual ingredients_simple field is not equivalent to an ingredient-level specification.

Without structured ingredient records and relationships, the system cannot reliably establish:

* Which supplier provides each ingredient.
* Which supplier product code corresponds to it.
* Whether an ingredient has changed.
* Which recipes are affected by that change.
* Whether associated cost and specification information needs updating.

This is a genuine capability gap, not simply a missing screen.

4. The capability register needs more disciplined status classifications

Document 03 is useful, but I would challenge several uses of the word operational.

For example:

Menu Explorer — Operational Inquiry Tool

This may be a functioning and populated interface. But it operates on a generated data snapshot. That does not establish that it is suitable for live operational decision-making.

Similarly:

Menu Review — Operational Review Tool

This is a stronger claim because it has persistence and an actual file-modification capability. Nevertheless, the documentation does not establish multi-user reliability, access control, backup procedures or a complete production deployment model.

I recommend distinguishing these statuses:

Status	Meaning
Implemented	Functionality exists in the code
Tested	Functionality has been exercised successfully
Populated	Relevant data exists
Persistent	Changes survive refreshes and restarts
Integrated	It exchanges data with another component
Operationally validated	It has been demonstrated in an actual working operational process

These should be independent attributes rather than a simple progression.

A component can be implemented, tested and populated without being operationally validated.

One other point: Document 03 labels several Menu Explorer capabilities as code-verified, including the allergen matrix, guest filtering and cross-venue comparison. That is useful evidence, but it does not establish the accuracy or completeness of the underlying data.

The distinction between a functioning calculation and a reliable operational result must remain explicit.

5. Document 04 contains some assumptions that should be separated from observed workflows

The workflow maps are useful because they translate technical components into the activities of an F&B Coordinator.

However, they sometimes describe a hypothetical ICG operating procedure as though it were an established business process.

For example:

* A creative agency uploads a new seasonal menu.
* A coordinator performs a particular review sequence.
* An executive chef investigates recipe discrepancies.
* A coordinator emails site chefs to resolve missing information.
* A particular person owns a particular stage.

These are plausible operational scenarios, but the codebase cannot establish that these are ICG’s actual procedures.

I would introduce a separate classification:

Illustrative operational workflow — not verified against ICG’s internal procedures.

There is another technical issue.

Document 04 describes cross-venue variance auditing as a real-time process and says it was tested under one second.

The underlying architecture described elsewhere is a generated JavaScript bundle loaded into the browser.

The accurate description would be:

Client-side comparison against the latest generated data snapshot.

It may execute extremely quickly, but it is not necessarily real-time in the operational sense.

6. Document 06 moves too quickly into regulatory decisions

This is the most important scope issue.

You previously specified that regulatory and allergen research should remain deferred at this stage.

Document 06 introduces:

* A mandatory critical-blocker classification for unset allergen information.
* Specific guest-facing filtering restrictions.
* A proposed compliance governance rule.
* An assertion that Kafoodie is authoritative for allergen and nutrition information.

These may eventually be appropriate subjects for a dedicated regulatory and data-governance review. They should not be decided in the current architecture phase.

In particular, an unset allergen field is evidence of missing information. It does not, by itself, establish the appropriate operational or regulatory classification of the product.

The technical assessment should record:

* Where allergen information originates.
* How it is represented.
* Whether missing information is detectable.
* Whether the interface exposes that state.
* Whether the information is linked to a recipe or product.
* Whether the system preserves provenance.

The policy for what happens next should remain undecided.

I would remove GAP-02 from the immediate development priorities and replace it with:

GAP-02 — Data provenance and verification status

This keeps the technical investigation moving without prematurely establishing a regulatory rule.

The distinction is that the workspace already demonstrates substantial capability in information acquisition, reconciliation, quality control and comparison.

Its weaker areas are ongoing operational management, shared records, workflow coordination and external-system integration.

That is a much more useful assessment than simply saying that some screens are complete and others are not.

8. The next documentation step

I would not ask the agents to implement the priorities in Document 06 yet.

First, I would request one additional verification pass focused on the contradictions and uncertainties.

The next deliverable should be:

Document 07 — Architecture Verification and Evidence Reconciliation

It should contain:

1. Hosting boundary: Remove Netlify from the actual application architecture.
2. Runtime verification: Establish exactly how the local application starts and which services it requires.
3. File-path verification: Resolve the two Markdown directory descriptions.
4. Database verification: Confirm the actual SQL engine, file location, tables, indexes, persistence and which components access it.
5. Build verification: Establish the two build pipelines, their inputs, outputs and execution dependencies.
6. Generated data verification: Establish whether venue.json is a complete output, a partial representation or a candidate future data layer.
7. Evidence reconciliation: Identify contradictions across Documents 01–06 and correct them.
8. Operational assumptions: Separate demonstrated software workflows from hypothetical ICG business procedures.

The agents should not change the application while doing this.

Overall assessment

The documentation has uncovered something more substantial than a collection of hospitality interface prototypes.

There is already a meaningful technical foundation:

* Data acquisition from multiple sources.
* Menu document quality control.
* Structured recipe and menu information.
* Automated matching between printed dishes and recipe records.
* Cross-venue comparison.
* Generated venue-level data structures.

But the architecture currently stops short of connecting those capabilities into a shared operational management system.

The central opportunity is not to add more AI or more interfaces. It is to establish reliable relationships between the information that already exists, the people responsible for maintaining it, and the operational decisions that depend on it.

That is the principle I would preserve throughout the remaining assessment: map the existing capability accurately before deciding what should be built next.
