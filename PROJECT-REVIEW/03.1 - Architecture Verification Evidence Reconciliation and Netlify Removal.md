Architecture Verification, Evidence Reconciliation and Netlify Removal

1. Objective

Review the existing project architecture, reconcile the findings documented in Documents 01–06, and remove Netlify completely from the project.

Netlify is not part of the actual application architecture. It was used exclusively to host development duplicates of interfaces so that remote agents could access and inspect them.

It is not required for the application’s operation.

We have therefore decided to remove Netlify entirely from the project and establish a cleaner, locally focused working environment.

This instruction authorises the removal of Netlify-specific project infrastructure and references. It does not authorise the removal or alteration of actual application functionality.

2. Architecture Verification

Before making changes, inspect the project and produce a verification manifest covering the following areas.

2.1 Actual application architecture

Establish and document:

* The actual application entry points.
* Required local services and runtime processes.
* Python servers and their responsibilities.
* The SQL database engine, location and schema.
* The actual data directories and file dependencies.
* API endpoints and their consumers.
* Build scripts, their inputs and outputs.
* Dependencies between the interfaces and backend components.

Distinguish actual application components from development infrastructure.

2.2 File-path verification

Investigate the relationship between:

* pages/menus_md/
* inncollectiongroup.com_root/menus_md/

Identify:

* Which directory is currently read by the application.
* Which directory is modified by review operations.
* Which directory is read by build scripts.
* Whether the contents are identical or have diverged.
* Whether either directory is redundant.

Do not delete or consolidate either directory as part of this instruction. Report the evidence and recommend the appropriate next action.

2.3 Database verification

Verify:

* Database engine.
* Actual database file location.
* Tables and columns.
* Indexes and constraints.
* Current records.
* Which application components read or write to it.
* Whether data persists between application restarts.

Do not assume that a generated JSON file is the application’s database or source of truth.

2.4 Build pipeline verification

Inspect all build scripts and establish:

* How many distinct build pipelines actually exist.
* Their source inputs.
* Their generated outputs.
* Whether generated outputs are consumed by any interface.
* Whether the pipelines depend on one another.
* Whether any pipeline contains Netlify-specific logic.

Reconcile the discrepancy between the previously documented two and three build pipelines.

2.5 Generated data verification

Investigate venue.json and related generated artefacts.

Establish:

* Which sources contribute to the generated data.
* Which fields are derived from which sources.
* Whether the output is complete or partial.
* Whether any application component actually consumes it.
* Whether it should be understood as a generated data artefact rather than an authoritative source.

Do not designate a global source of truth without evidence. Authority should be established at the individual data-domain or field level.

3. Complete Netlify Removal

3.1 Removal scope

Identify and remove all Netlify-specific project infrastructure, including, where present:

* The Netlify deployment directory or duplicate project.
* netlify.toml.
* netlify/ directories.
* Netlify serverless functions.
* Netlify-specific API implementations.
* Netlify build and deployment configuration.
* Netlify-specific redirects and headers.
* Netlify deployment scripts.
* Netlify-specific environment configuration.
* .netlify/ local metadata and generated files.
* Netlify-specific dependencies that are no longer required.
* Netlify-specific documentation and deployment instructions.
* References to Netlify in project configuration, scripts and documentation.

The removal must be comprehensive. Do not leave an obsolete Netlify deployment structure or an unused parallel application implementation behind.

3.2 Important distinction

Remove Netlify-specific infrastructure, not the actual functionality that happened to be exposed through it.

For example:

* If a Netlify function duplicates functionality already implemented by the local Python server, remove the Netlify function.
* Preserve the local Python server and its actual API endpoints.
* Preserve the SQLite database and its data.
* Preserve the application interfaces.
* Preserve the build scripts and their inputs and outputs.
* Preserve shared assets and source files.
* Preserve any component that is required by the actual local application, even if it was previously referenced by Netlify.

If a file contains both Netlify-specific and application functionality, isolate and remove only the Netlify-specific portion.

Do not delete an entire directory merely because its name or contents contain a Netlify reference if it also contains actual application resources.

3.3 References and dependencies

Search the entire project for:

* netlify
* netlify.app
* netlify/functions
* Netlify deployment commands.
* Netlify-specific API URLs.
* Netlify-specific environment variables.
* References to serverless execution or Lambda that exist only to support the former Netlify implementation.

Remove obsolete references from the project documentation, configuration and scripts.

Do not indiscriminately replace or rewrite unrelated technical references.

The final application architecture documentation must describe the actual local application, not its former development hosting arrangement.

3.4 External deployment

This instruction concerns the project repository and local working environment.

Do not assume that deleting local Netlify files automatically deletes an externally hosted Netlify site or account configuration. Do not attempt to access, modify or delete external accounts or services.

Report any external deployment or configuration that may still exist separately.

4. Execution and Safety Requirements

Perform the work in the following order:

1. Inspect the repository and identify the complete Netlify removal scope.
2. Produce a manifest of every file and directory proposed for removal.
3. Identify any shared files that require selective editing rather than deletion.
4. Identify any dependencies that could affect the local application.
5. Preserve the existing application and database state.
6. Remove the Netlify-specific infrastructure.
7. Remove obsolete Netlify references.
8. Run relevant checks to establish that the local application still works.

Before destructive changes, ensure that the current working state is recoverable through an existing version-control checkpoint or an appropriate backup.

Do not delete user data, source documents, menu files, generated application data or database records.

Do not redesign, refactor or rewrite unrelated application components during this cleanup.

5. Post-removal Verification

After removal, verify:

* The local Python application starts successfully.
* The local API endpoints still respond.
* Menu Review can still access its required files and database.
* Review-state persistence still works.
* Menu Explorer can still load its generated data.
* Discovered Media can still perform its supported local export workflow.
* Existing build scripts still execute where appropriate.
* No remaining application component requires Netlify.
* No obsolete Netlify deployment configuration remains in the project.

Do not report a component as working unless it has actually been tested. Clearly distinguish static inspection from execution tests.

6. Required Deliverables

Produce the following documentation.

A. Netlify Removal Manifest

A complete record of:

Path	Classification	Action	Reason	Application impact
Exact path	Netlify-only / mixed / shared	Removed / edited / retained	Explanation	None / tested / unresolved

Include all deleted files and directories, all edited files, and all Netlify-related files intentionally retained.

B. Architecture Verification Report

Reconcile Documents 01–06 and provide evidence-based conclusions on:

* Actual application architecture.
* Runtime and services.
* File-system structure.
* Database implementation.
* Build pipelines.
* Generated data.
* API relationships.
* Interface dependencies.

C. Final Netlify Reference Audit

Report:

* Number of Netlify-specific files and directories removed.
* Number of shared files edited.
* Remaining Netlify references, if any.
* Reason for each retained reference.
* Whether the local application has any remaining Netlify dependency.

D. Local Application Verification Report

List each tested component, the test performed, the result and any unresolved issue.

E. Updated Project Architecture Map

Produce a clean architecture map that excludes Netlify entirely and represents only the actual application, its local runtime, data sources, database, APIs, build pipelines and interfaces.

7. Final Constraints

* Do not implement new functionality.
* Do not introduce new frameworks or infrastructure.
* Do not migrate the database.
* Do not restructure unrelated directories.
* Do not delete either Markdown directory pending the separate path investigation.
* Do not make regulatory or allergen-policy decisions.
* Do not represent hypothetical ICG operational workflows as verified company procedures.
* Do not invent integrations with EPOS, procurement or other external systems.
* Do not claim that a proposed capability is implemented.
* Preserve the distinction between observed, code-verified, database-verified, tested, inferred, proposed and unknown.

The intended outcome is a clean, self-contained local application with no Netlify infrastructure or dependency, accompanied by a technically verified architecture record.
